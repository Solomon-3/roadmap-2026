1) INNER JOIN vs LEFT JOIN
Inner join strict
SELECT users.name, products.name
FROM users
INNER JOIN products
ON users.id = products.user_id;   this returns # ONLY users who HAVE products

Left join inclusive
SELECT users.name, products.name
FROM users
LEFT JOIN products
ON users.id = products.user_id;  this returns all users even if they dont have products

3) FILTERING
lets move from show everything to only show what i care about
#####################################
week7db=# SELECT users.name, COUNT(products.id) AS total_products FROM users LEFT JOIN products ON users.id = products.user_id GROUP BY users.name HAVING COUNT(products.id) > 0;
   name    | total_products 
-----------+----------------
 salvatore |              2
 Neo       |              1
(2 rows)
###################################

the key difference is that WHERE -> filter rows                    => filters before grouping 
                           HAVING -> filter aggregated results     => filters after grouping

EXECUTION ORDER
A) FROM / JOIN
B) WHERE        <- filters raw rows
C) GROUP BY     <- creates groups
D) HAVING       <- filters groups
E) SELECT

WEEK 8 DAY 2 - INDEXES (Performance)
in the event tht we have 10 mil users, we would have a degredation where results move from milliseconds to seconds or even worse

1) so right now our query SELECT FROM JOIN ON behind the scenes (no index)
    for EACH user
         scan ALL products
so for 10 mil users and 10 mil products
thats 10,000,000 * 10,000,000 = ehhh

2) what an INDEX does
no index -> search a book word by word
index    -> jumping straight to the page

week7db=# CREATE INDEX idx_products_user_id ON products(user_id);
CREATE INDEX

now instead of scan entire products table, jump directly to matching user_id
JOIN performance depends heavily on indexed columns
in my case products.user_id <- MUST Be indexed
